## 修改前後與審核門檻

正式環境這批影響目前均為 **0 → 0 筆修改**。

只有隔離空資料範例通過以下完整流程：

| 項目 | 刪除前 | 刪除後 |
|---|---:|---:|
| 指定測試主播公開 descriptor | 1 | 0 |
| 指定測試主播設定物件 | 1 | 0 |
| 指定測試主播 Space mapping | 1 | 0 |
| 玩家 Account／其他主播 | 原值 | 原值 |
| 歌曲／玩家／帳務／演唱／私訊／勳章 | 0 個目標依賴 | 不修改 |
| 既有 Audit／別人網址與舊 QR | 原值 | 原值 |
| 新增刪除管理 Audit | 0 | 1 |
| Space／registry revision | 原值 | 各 +1 |

預檢回應包含 `confirmationToken`（只作版本摘要，不是登入憑證）、Space 與 registry revision、schema fingerprint、名稱和精確目標 ID。真正刪除前必須重新檢查；任何版本或關聯變更都要求重新預覽。相同 operation ID 只執行一次，重用但內容不同會拒絕。

## 為什麼不直接套用刪除 SQL

`ops/test-streamer-delete-proposed.sql` 目前是**本機提案**，不屬於之前「6 欄、稽核表及管理函式」的非破壞性核准範圍。新的唯讀預檢函式亦未套用正式環境。

硬刪原型還有兩道隔離：預設拋出 `DELETE_PROTOTYPE_ONLY`；沒有授予 service_role EXECUTE。只有本機測試資料庫所有者顯式開啟隔離旗標才能測試。**這不是可部署的正式永久刪除函式**，不能直接移除保護來宣稱完成。

正式可執行版仍需：針對明確 ID 核對玩家 JSON、備份、付款、actor／target 等間接關聯；確認歷史查詢不依賴將刪除的 mapping；完成實際多連線寫入與刪除競態測試；列出每一筆的精確影響後，取得永久刪除與新增 migration 的確認。保留舊網址或 Audit 時不能刪除它們或透過 cascade 連帶刪除。

## 權限、鎖定與回復風險

- 預檢函式 server-only，browser 角色無 EXECUTE；傳入的 Account 必須由伺服器驗證 session 取得。
- 生產版不能只在 Edge 讀權限後再分開刪除；必須在同一交易鎖定並重新核驗。
- 空資料原型刪除時鎖 revision、Space、mapping 與 meta table；這個廣域 meta 鎖尚未完成正式多連線／延遲評估，因此保留隔離限制。
- 正式永久刪除之後不能以「還原封存」恢復；需使用經核准且受保護的精確 descriptor／設定／mapping 備份回復。既有原始 Audit 保留，不匯出私人內容。提案的管理 Audit 保存刪除預檢摘要，不足以當完整還原備份，需補妥後才可上正式。
- rollback migration 應僅撤銷新 RPC 使用權與 UI 入口，不回滾既有業務資料、不刪管理 Audit。
